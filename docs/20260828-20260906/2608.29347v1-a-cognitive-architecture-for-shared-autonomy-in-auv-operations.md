## 摘要
操作员对于遥控潜水器（ROV）的操作仍然至关重要，但常常面临态势感知能力低和工作负载高的问题，这两者都对安全性产生负面影响。本文提出了一种由本体论和多个大语言模型（LLM）组成的认知架构，以在任务的所有阶段为操作员提供辅助。每个LLM都基于本体论中的领域特定信息进行基础设定，并赋予简单的角色，从而构建一个能够在操作的所有阶段为操作员提供支持的系统。我们旨在证明，将两者结合使用可以使决策建立在相关领域知识的基础上，同时也受益于LLM的推理能力。我们的框架能够判断给定的无人水下航行器（UUV）是否能够执行某项任务，进行任务规划，并在仿真中执行给定的任务。操作员可以参与规划和执行，以确保生成的计划有效，并确保执行期间车辆行为安全。我们比较了不同的LLM，如Llama3、GPT-OSS和Qwen2.5，以确定哪些最适合我们框架中的不同角色。我们发现GPT-OSS在可行性评估、规划和执行方面表现最佳，而Qwen2.5最适合从自然语言输入中识别任务类型。

## Abstract
Operators remain essential to Remotely Operated Vehicle (ROV) operation, yet often suffer from low situational awareness and high workload, both of which negatively affect safety. This paper presents a cognitive architecture consisting of an ontology and multiple Large Language Models (LLMs) to assist the operator at all stages of the mission. Each LLM is grounded with domain-specific information from the ontology and given a simple role to create a system that can support the operator at all stages of an operation. We are aiming to prove that using the two together will allow decisions to be grounded in the relevant domain knowledge, but also benefit from the reasoning capabilities of the LLM. Our framework determines if a mission is possible for a given Unmanned Underwater Vehicle (UUV), performs mission planning, and executes a given mission in simulation. The operator can be involved in planning and execution, ensuring the resulting plan is valid and that the vehicle behaves safely during execution. We compare different LLMs, Llama3, GPT-OSS, and Qwen2.5, to determine which are best suited to the different roles within our framework. We find that GPT-OSS performs best for feasibility assessment, planning, and execution, while Qwen2.5 is best suited to identifying mission types from natural language input.

## 2. 论文提出的方法论（核心思想、关键技术细节、流程）

### 核心思想

系统架构由三大组件组成：

1. **本体论（Ontology）**
2. **一组智能体 LLM（Agentic LLMs）**
3. **LLM 监督器（Supervisor）**

所有组件通过 **ROS（Robot Operating System）** 通信，ROS 本身也提供额外的事实约束层，用于“落地” LLM 决策。

### 各组件功能详解

**（1）本体论**

构建一个专门面向水下无人系统的领域本体，存储三类信息：

- **任务评估相关**：水下航行器实例（含硬件、软件）、可执行任务类型及所需能力（如导航、局部定位、路径规划、3D 稠密建图、操作能力、通讯能力等）之间的所属与依赖关系。
- 用 **SWRL 规则**完成从“组件组成”到“能力/胜任力”的自动推理。示例规则（式 1）：
  `Platform(?c) ∧ hasCapability(?c, Localisation) ∧ PathPlanningAlgorithm(?d) → hasCapability(?c, PathPlanning)`
  含义：只要平台自身具备定位能力并搭载路径规划算法，即可推定其具备路径规划能力。
- **任务规划相关**：存储具体动作（action）的**前序条件（pre-conditions）与后置条件（post-conditions）**；动作与任务类型相互关联；同时存放**硬件约束**（如机械臂最大操作距离）和**环境约束信息**（如风电机组、管道等结构物坐标），以保证计划的物理可行性。
- **任务执行相关**：存储 ROS 动作/服务的调用信息、请求参数。参数被划分为：
  - 由 **LLM 动态决定**（如避碰距离、绕行半径），
  - 由**本体静态提供**（如被检结构的位置）。
- 这样能确保 LLM 只需要做逻辑选择，不需要自己去推理硬件组成或“发明”行为实现。

本体图（图 2）展示了任务类型、动作实例、软件实现之间的连接关系。

**（2）LLM 角色划分（Agentic LLMs）**

- **角色 1：任务评估**
  - 由两个 LLM 合作完成：
    1. 第一个 LLM 负责从自然语言描述中**识别具体任务类型**；
    2. 第二个 LLM 查询本体中该任务必需能力与 UUV 实例的推断能力，比较两者。
  - 输出三类结果：**完全可行（fully possible）、部分可行（partially possible）、不可行（impossible）**。
- **角色 2：任务规划**
  - 一个 LLM 基于系统提示中提供的任务相关的动作与前/后置条件，生成结构化计划。
  - **操作员可在计划过程中进行协作式反馈**，要求增补、删减或修改步骤；最终计划在操作员批准后交给执行层。
- **角色 3：任务执行**
  - 执行 LLM 采用**工具调用（tool-calling）架构**，在仿真环境中调用预设 ROS action 和服务，而不是让 LLM 自行生成控制器代码。
  - 长时行为通过 **ROS action** 实现（可接收反馈，可取消）；瞬时行为用 **ROS service** 实现。
  - 操作员可**实时介入、批准或修改每一步工具调用**。
- **角色 4：诊断与异常处理**
  - 同时运行的诊断 LLM 接收本体信息（必要时也通过 Web 搜索），并结合操作员协作分析故障原因、推荐修复或缓解方案，若有必要则驱动重规划。
  - 与执行层的 action 取消机制形成闭环，支持“执行中发生意外 → 重计划”的共享决策。

### 整体运行流程（文字描述）

用户给出自然语言任务描述 → 第一个 LLM 识别任务类型并与本体关联 → 第二个 LLM 比较本体中的任务能力需求与 UUV 推断能力，输出可行性报告 → 规划 LLM 依据本体中的动作/条件生成计划初稿 → 操作员提出修改意见并协同完善 → 执行 LLM 通过工具/ROS action 执行计划 → 执行中发生异常时诊断 LLM 分析故障并给出修复/缓解建议，必要时执行重规划 → 全程操作员保留最终批准/叫停权限。

## 6. 实验结果（核心数据与趋势）

### 6.1 任务类型识别

- 在同时包含“检测”与“阳极测试”的复合任务描述中，**所有测试 LLM 均能正确识别出两类任务**（表 II 显示识别正确率为 100% 或接近 100%，论文中未报告失败案例）。
- 说明：这一环节本身对 LLM 挑战不大，真正的难点在于将识别出的任务与本体中的能力需求正确关联。

### 6.2 任务评估（可行/部分可行/不可行判定）

- **加入本体信息后，所有模型的表现均有显著提升**。尤其是 Qwen2.5 与 GPT-OSS，能在绝大多数情况下准确区分“完全可行”“部分可行”“不可行”三种状态。
- **禁用本体信息时，模型普遍高估了平台能力**，常把缺少机械臂或缺少建图算法的平台误判为“完全可行”。这验证了论文的核心假设：仅靠 LLM 内部知识无法可靠判断真实机器人平台的物理能力，本体知识必不可少。
- Llama3 即便在本体提示下，判定正确率也明显偏低，且回答格式不稳定。

### 6.3 任务规划

- 有本体提供的动作前置/后置条件时，规划质量明显更高：步骤间前置条件满足率接近 100%，最终计划的目标完成率高、冗余步骤少。
- 无本体条件下，模型经常生成**逻辑上可行但物理上不可执行**的计划，例如在未完成 SLAM 初始化前就要求进行路径跟踪，或凭空编造不存在的动作名称。
- 在模型对比上，Qwen2.5 与 GPT-OSS 表现接近并优于 Llama3；Llama3 还会出现步骤遗漏或输出格式不满足后续解析要求的问题。

### 6.4 任务执行

- 只有 Qwen2.5 与 GPT-OSS 被纳入任务执行对比（Llama3 因 JSON 工具调用格式无法解析而被作者剔除）。
- 在执行预设“最优检测计划”时，两者在大多数运行中都能正确按顺序调用动作；少数错误表现为：
  - 动作名错误（模型自行“改名”）；
  - 参数缺失或参数类型错误（如把位置坐标写成字符串）；
  - 时机错误（如过早启动路径跟踪）。
- 在引入操作员协作（人工纠正）后，两项模型均能快速修正并完成全部执行流程。
- 论文未给出执行成功率的具体数值表格，而是用定性描述说明“多数运行可顺利完成，少数需要人工干预修正”。

### 6.5 本体知识 vs. LLM 通用知识：核心结论

- 论文通篇反复印证一个结论：**仅靠 LLM 的通用知识与推理，不足以支撑安全、可信的 AUV 共享自主操作**；将精细建模的本体领域知识注入提示后，LLM 可接近实用水平。
- 多智能体角色划分（将任务分解为评估、规划、执行、诊断）能有效降低单一大模型的任务复杂度，从而减少幻觉与格式错误。

## 7. 论文的局限性（作者承认与隐含不足）

1. **仿真环境局限**：所有实验仅在 Stonefish 仿真器中完成，未在真实水下环境中测试，也没有考虑水下通讯延迟/中断、洋流扰动、声呐噪声等实际物理因素。
2. **模型与规模有限**：仅测试了 3 个本地模型，未覆盖主流更大参数模型（如 GPT-4、Claude 等）；受 8 GB 显存制约，很可能使用了量化/小参数量模型，结论可能无法推广到更强模型。
3. **任务范围狭窄**：只验证了“结构检测+阳极测试”一种应用场景，对更复杂的多目标任务、动态任务或意外事件（如机械臂卡滞、传感器漂移）未被系统测试。
4. **主观评估指标**：规划质量的“最优性”、执行中的“错误动作数”等由人工评定，缺乏客观量化标准，多人评定一致性（inter-rater reliability）未报告。
5. **无实时性/性能数据**：未报告 LLM 推理耗时、端到端决策时间、与 ROS 通信的延迟，无法判断系统能否满足现场 AUV 操作的实时性要求。
6. **“诊断与异常处理”角色未展开实验**：论文在架构中提出了诊断 LLM，但实验部分并未对此角色进行独立验证，功能仅停留在设计层面。
7. **操作员信任与合作仅有定性设计**：虽然有“操作员批准/修改/介入”机制，但未设计人机交互实验来衡量信任度、操作员负荷或协作效率的提升。

## 8. 总体评价与启示

- **创新点**：将本体论与 LLM 组合，形成“角色分工、由本体严密约束、由监督器调度”的共享自主架构，为水下机器人的人机协作提供了一种可行范式。
- **工程价值**：系统构建于 ROS 之上，LLM 仅做高层逻辑决策，低层运动控制仍由传统安全算法接管，这种“混合式”设计极大降低了 LLM 直接控制硬件的风险。
- **可解释性**：本体中 SWRL 规则可生成显式论证（例如“该 UUV 具有 A 和 B，因此具有能力 C”），支撑 LLM 给出的可行性结论，有助于操作员建立信任。
- **未来方向**（基于文中逻辑可推测）：扩展真实海试验证、增加更丰富的任务本体、引入记忆机制让 LLM 从历史任务中学习、强化诊断智能体并将异常样本纳入重规划闭环、引入更高质量大模型或微调领域专用小模型。

**总结**：这是一篇以系统架构设计和仿真验证为主的研究论文，核心贡献是提出并验证了“本体为骨架、LLM 为大脑、流程为闭环”的水下机器人共享自主认知架构。实验结果表明该框架在任务评估、规划与执行环节能够有效弥补纯 LLM 的不足，但从仿真到真实部署仍存在明显距离。其严谨的模块化设计和对人机协作流程的细粒度建模，使其成为 AUV/AUV 操作智能辅助系统的有参考价值的原型工作。
