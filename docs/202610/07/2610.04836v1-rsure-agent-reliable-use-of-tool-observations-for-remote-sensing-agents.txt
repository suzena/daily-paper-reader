We refer to their judgments and quantitative results about ground objects as tool observations. I. I NTRODUCTION 

Earth observation is essential for understanding the dy-namics of the Earth system. Remote sensing (RS) agents now automate Earth observation tasks through planning and external tool use [1], [2]. Unlike end-to-end methods that rely on a single model, agents combine specialized tools according to task requirements. They also decide when to use their own capabilities and when to call external tools. During execution, agents use visual perception, spatial measurement, and raster analysis tools to obtain judgments and quantitative results about ground objects. These results include object categories, arXiv:2610.04836v1 [cs.CV] 4 Oct 2026 2

geometric distances, areas, and remote sensing products. Fol-lowing the definition of observations in Earth observation [3], [4], we refer to these outputs as tool observations . The term differs from observation in agent paradigms such as ReAct [5], where it refers to any feedback from tool execution. Existing remote sensing agents typically build on general-purpose agent frameworks [6], [7]. Their methods combine task planning [8], [9], [10], knowledge retrieval and mem-ory [11], and tool calling [12], [13] to solve complex tasks. For tool use, these methods focus mainly on correct selection and successful execution. Tool observations are usually passed directly to subsequent reasoning once execution completes successfully [14], [15]. However, successful execution does not guarantee reliable observations. Studies of semantic seg-mentation, object detection, hyperspectral classification, and target extraction link result reliability to scene complexity, image quality, and uncertainty in model predictions [16], [17], [18], [19]. If the agent accepts an incorrect observation, later steps may rely on it. The error can propagate through the workflow and cause task failure. We analyze 1,229 agent execution trajectories from three benchmarks to quantify this problem. These are Earth-Bench [8], ThinkGeo [20], and TerraLogic [21]; Section III presents the analysis. On each benchmark, at least 88.1% of tasks depend on tool observations. Among these tasks, at least 22.7% contain incorrect observations despite successful tool execution. On each benchmark, errors reach the final answer in at least 82.0% of tasks containing incorrect observations. These findings identify tool observation reliability as a recur-ring challenge in remote sensing agent workflows. To address this problem, we propose RSure-Agent to use tool observations more reliably and limit the impact of tool observation errors on subsequent reasoning. Fig. 1 illustrates RSure-Agent in a task that measures the area of a small vehi-cle. We design a verifiable observation protocol that requires each tool to return process evidence with its observation. Process evidence exposes intermediate results and computation conditions for verification. The verifier checks whether this evidence supports accepting the current observation. We build a task–tool reliability prior from offline trajectories. The prior records how different tool configurations have performed on each task type. When the prior is low, the verifier checks the evidence more strictly. When the prior is high, the observation must still be supported by the image and process evidence. After a tool returns an observation, RSure-Agent combines the two sources of information to accept it, request additional evidence, or reject it. This reduces the effect of incorrect observations on subsequent reasoning. We evaluate RSure-Agent on three remote sensing agent benchmarks: EarthBench, ThinkGeo, and TerraLogic [20], [8], [21]. We also construct CHOICE-420 from CHOICE [22] to evaluate remote sensing visual question answering (VQA). On agent benchmarks, RSure-Agent achieves competitive task per-formance. Relative to the base configuration with verification and the prior disabled, RSure-Agent reduces the error propaga-tion rate by 21.3 to 25.9 percentage points. On CHOICE-420, it improves overall accuracy over direct answering by 5.71 percentage points on average across 11 backbone models. Our main contributions are as follows:  

> •

We quantify tool observation reliability across three RS agent benchmarks. On each benchmark, at least 88.1% of tasks depend on tool observations. We propose RSure-Agent, a framework limiting how in-correct tool observations affect subsequent reasoning. Its verifiable observation protocol requires process evidence from tools for verifying observations before acceptance.

A. Remote Sensing Agents and Benchmarks 

Remote sensing agents automate Earth observation tasks by understanding tasks, planning, and calling external tools [1], [2]. They combine specialized tools as needed for image per-ception, spatial analysis, and quantitative computation through multi-step interaction. This enables complex spatiotemporal reasoning and quantitative analysis [8], [12], [23]. Early work explores how to combine remote sensing models with natural language interaction. Remote Sensing ChatGPT calls remote sensing models through dialogue [13]. Tree-GPT enables interactive interpretation of forest remote sensing images [24]. Change-Agent combines change perception with language interaction to interpret land surface changes [25]. For task planning and execution, RS-Agent converts user intent into executable sequences of remote sensing tool op-erations [12]. Earth-Agent performs quantitative Earth obser-vation analysis through multi-step tool calls and working-memory updates [8]. To handle more complex analysis, multi-agent collaboration has been introduced to this field. Ge-oMMAgent and GeoLLM-Squad divide knowledge retrieval, target perception, and integrated reasoning among several agents [2], [9]. For long-horizon tasks, HiRS-Agent uses a hi-erarchical architecture with dynamic replanning [26]. RingMo-Agent and RingMo-Claw also explore autonomous execution and capability extension for remote sensing tasks [27], [28]. Tool organization and the reuse of past experience are another research focus. GeoLLM-Engine integrates geospatial APIs, map operators, and external knowledge into a unified tool environment [29]. OpenEarthAgent integrates a remote sensing tool chain and builds standardized tool-call trajecto-ries [14]. For tool retrieval and selection, RS-Claw retrieves the required tools level by level through a skill tree [30]. RemoteAgent decides by itself whether to reason directly or to call specialized tools [23]. REMSA selects suitable foundation models under given constraints [31]. OpenEarth-Agent further explores creating tools on demand [32]. In addition, RSMeM, 3

GeoEvolver, and GeoForge use past trajectories and execution experience to improve later task solving [11], [10], [33]. Agents are also built for specific applications. RescueADI decomposes disaster interpretation into coordinated perception and analysis tasks [34]. AirSpatialBot targets the recognition and retrieval of fine-grained vehicle attributes in aerial im-ages [35]. MineAgent and PEACE are designed for mineral ex-ploration and geological map understanding, respectively [36], [37]. Agents have further been applied to satellite observation scheduling. TSLC uses large language models (LLMs) to coor-dinate order-driven satellite task planning [38]. For large-scale agile Earth observation satellites, LLM agents are used to solve bi-level online order dispatching and dynamic scheduling [39]. Existing benchmarks evaluate remote sensing agents in terms of task completion, tool use, and the reasoning process. ThinkGeo focuses on image-driven tool chains, multi-step planning, and spatial reasoning [20]. EarthBench covers quan-titative Earth observation tasks on multi-source spectral data and remote sensing products [8]. TerraLogic examines hierar-chical geospatial reasoning and compositional analysis [21]. GeoMMBench systematically evaluates perception, knowl-edge use, and reasoning in multimodal geoscience tasks [2]. GeoLLM-Engine, UnivEARTH, and OpenEarth-Bench build diverse geospatial tool environments for evaluation [29], [40], [32]. TerraBench further studies agent reasoning over het-erogeneous Earth system data [41]. For specialized tasks, AirSpatialBot and PEACE provide benchmarks for aerial spatial question answering and geological map understanding, respectively [35], [37]. CHOICE evaluates perception and reasoning in remote sensing VQA [22]. In summary, prior work on remote sensing agents mainly focuses on task planning, tool selection, knowledge retrieval, and workflow execution. Less attention has been paid to whether the observations returned by normally executed tools are reliable. Munir et al. [15] note that remote sensing work-flows operate on georeferenced, multimodal, and temporally structured data. Reprojection, resampling, mosaicking, and aggregation change the underlying state and constrain later analysis, so errors can propagate through subsequent reason-ing. We quantify the propagation of tool observation errors on ThinkGeo, EarthBench, and TerraLogic and show its impact on remote sensing agents. 

B. Agent Verification 

Verification for general agents covers three levels: model reasoning, tool-call actions, and returned results [42], [43]. At the reasoning level, Reflexion [44], RetroFormer [45], and Self-Refine [46] correct generated content with self-reflection feedback or external evaluators. SCORE [47] stud-ies optimization with process rewards. Other work analyzes when self-correction works [48]. CRITIC [49] guides the correction of multimodal reasoning through interactive tool use. SPoRT [50] assigns a process reward to each reasoning step to guide trajectory optimization. SGV [51] addresses bias when multimodal models evaluate agent behavior. It first forms an independent expectation of the behavior and then uses it to evaluate candidate trajectories. RV-LLM [52] proposes a runtime verification framework to detect hallucinations. Tool-MVR [53] trains models on verified tool-call data and reflection samples to improve tool calling and error correction. Other studies analyze fault propagation and failure attribution in long-horizon reasoning [54], [55], [56], [57]. At the action level, ToolEmu [58] evaluates the potential risks of tool calls. ToolSword [59] detects malicious tool-call intentions. Relign [60] addresses hallucinations in tool selection and use by introducing actions such as deferring execution, asking for clarification, and changing the selected tool. Vigil [61] and ToolGate [62] check the completeness and safety of arguments before a call. AgentSpec [63], AgentLTL [64], Reason Less, Verify More [65], Reinforced Agent [66], and Verified Tool Calls [67] constrain execution with temporal logic rules or formal specifications. At the result level, Tools Fail [68] studies how to detect silent tool errors. RIVA [69] cross-checks the results of different tools to reduce the effect of wrong outputs on detection. EG-VAR [70] requires reasoning to rest on traceable evidence. Trust or Escalate [71] enables agents to abstain or escalate when the available evidence is insufficient. Existing remote sensing agents mainly improve execution reliability through feedback and rule checks. GeoMMAgent decides whether to output a conclusion or re-execute based on self-evaluation [2]. HiRS-Agent introduces step-level veri-fication and replanning [26]. CangLing-KnowFlow constrains workflows with tool preconditions and quality feedback, and triggers repair when anomalies occur [72]. In satellite task scheduling, TSLC checks feasibility using external rules [38]. In summary, existing studies verify agents at the level of rea-soning, actions, and execution results. Unlike work that verifies agent execution steps, checks tool outputs against images and task context, or cross-checks results between tools [26], [68], [69], we focus on the reliability of the observations returned by remote sensing tools. Remote sensing agents rely on visual perception, spatial measurement, and raster analysis tools, and most of their outputs are uncertain observations. Even under normal execution, these observations can be wrong because of scene complexity, image quality, and model prediction uncertainty. The errors can then propagate through subsequent reasoning. RSure-Agent builds its verification on two intu-itions. First, exposing the internal process of a tool helps judge whether an observation is trustworthy. We therefore define a verifiable observation protocol that requires tools to provide process evidence. Second, the past performance of different tool configurations on specific tasks can serve as a reference for verification. We therefore build a task–tool reliability prior. The framework verifies tool observations with both the process evidence and the prior, limiting the propagation of incorrect observations. III. E MPIRICAL ANALYSIS OF TOOL OBSERVATIONS

A. Metric Definitions 

Let T be the set of evaluated tasks. We define three task-level metrics. 

Observation dependence rate Rdep measures the fraction of tasks that use tool observations. Let Tdep ⊆ T be the subset of tasks in which at least one tool observation is used in subsequent reasoning. Then      

> Rdep =|Tdep ||T|.(1)

Observation error rate Rerr measures how often observa-tions are wrong when tools execute normally. An observation error means that the tool completes execution and reports no error, but the returned observation disagrees with the reference facts. Let Terr ⊆ Tdep be the subset of tasks with at least one observation error. Then     

> Rerr =|Terr ||Tdep |.(2)

This metric separates the execution status of a tool from the actual correctness of its observation. 

Error propagation rate Rprop measures how often awrong observation is adopted by subsequent reasoning and carried into a wrong final answer. Let Tprop ⊆ Terr be the subset of tasks in which a wrong observation is adopted by subsequent reasoning and the wrong final answer is consistent with that observation. Then     

> Rprop =|Tprop ||Terr |.(3)

This definition corresponds to the error propagation probability that AgentProp-Bench [73] measures for general tool agents. The difference is that we count naturally occurring errors rather than injected ones. 

B. Results 

Table I reports the statistics. We draw three findings. 

Remote sensing agents widely depend on tool observa-tions. Rdep is at least 88.1% on all three benchmarks. Tool observations are used in most tasks, indicating that remote sensing agents widely depend on them. 

Normal execution does not guarantee correct obser-vations. Rerr is 22.7%, 41.3%, and 39.8% on EarthBench, ThinkGeo, and TerraLogic, respectively. All these errors occur when the tool reports no anomaly. Error handling based on execution status cannot catch them. 

Wrong tool observations propagate at a high rate. 

Among tasks with observation errors, Rprop is at least 82.0%, and it exceeds 91% on ThinkGeo and TerraLogic. incorrect observations are often carried forward by subsequent reason-ing. This is consistent with the over-trust observed in general tool agents [68], [74], [75]. IV. M ETHOD 

To address the propagation of tool observation errors iden-tified in Section III, we propose RSure-Agent, an observation verification framework. It verifies each tool observation af-ter the tool executes and before the backbone model reads the observation. Fig. 2 shows the overall architecture. The verifiable observation protocol requires tools to return the execution status and process evidence with each observation. Online verification first runs deterministic rule checks and then queries the reliability prior for the task and tool configuration. The verifier uses the same model as the backbone but a separate context. It combines the input images, the process evidence, and the prior to accept the observation, request additional evidence, or reject it. Accepted observations enter the verified history for final reasoning, while ongoing tasks continue planning and tool execution based on feedback.

C. Task–Tool Reliability Prior 

The deterministic rules used here check execution status and computation conditions, but do not directly assess whether an observation matches the image content. Tool performance also varies with the task type. For example, an open-vocabulary perception tool can judge whether a target exists but may miss objects when counting dense small targets. Because online verification can not access the current observation’s ground truth, RSure-Agent uses offline calibration results as a historical reference. The prior reflects how a tool configuration has performed on the task type and helps the verifier check current evidence. D. Online Verification 

Online verification applies to the observations returned by perceive , measure , and execute . The system first runs deterministic rule checks and then performs semantic verification on the observations that pass. A. Experimental Setup 

Datasets. We evaluate on ThinkGeo [20], EarthBench [8], and TerraLogic [21], with 436, 248, and 545 test tasks, respectively. ThinkGeo tests structured tool use, multi-step planning, and spatial reasoning on remote sensing images. EarthBench tests autonomous planning and multi-step tool calls for quantitative analysis of RGB images, spectral data, and remote sensing products. TerraLogic focuses on hierarchi-cal geospatial reasoning through long compositional analysis chains. We also construct CHOICE-420 from the 21 multiple-choice task types in CHOICE [22]. We exclude the other two of its 23 task types, visual grounding and referring expression segmentation, which require bounding boxes or segmentation masks. This keeps the answer format consistent across the selected tasks. We select 20 samples per type, yielding 280 perception tasks across 14 types and 140 reasoning tasks across 7 types. The resulting benchmark contains 420 tasks, with task definitions provided in Appendix D. The reliability calibration set does not overlap with any evaluation set. 

Evaluation Protocols and Compared Methods. For ThinkGeo, we follow the official protocol, using GPT-4o-mini to judge answer correctness based on each query’s evaluation question. We report final answer accuracy (Ans.) and image-grounded answer accuracy ( Ans I ), both of which are end-to-end metrics. For EarthBench, we report end-to-end accuracy (Acc.) in Autonomous Planning (AP) mode. For TerraLogic, we report final answer accuracy (AnsAcc). On CHOICE-420, we report Overall, Perception, and Reasoning accuracy. The compared methods include Thinkgeo-Agent [20], Hier-aPlan [21], Earth-Agent [8], OpenEarth-Agent [32], HiRS-Agent [26], and RS-Claw [30]. We use results from their original papers, including both accuracy and efficiency for Earth-Agent. On CHOICE-420, direct answering by each backbone model serves as the baseline for measuring accuracy changes with the full framework.

C. Ablation Study 

Core component ablation. We use GPT-5 as the backbone and enable observation verification and the task–tool reliability prior in turn. When the prior is turned off, the verifier still checks the current image and process evidence but does not receive the historical reliability score. When both are turned off, the configuration becomes RSure-Base in Section V-A. All configurations use the same tool set and call budget. The first row of Table VI is RSure-Base. Compared with RSure-Base, the full RSure-Agent improves the four metrics by 2.5, 7.8, 3.2, and 5.0 percentage points, and the gains cover all three benchmarks. Without the reliability prior, enabling observation verification alone also improves every metric. On ThinkGeo, Ans. and Ans I improve by 1.4 and 4.7 percentage points. EarthBench and TerraLogic improve by 2.0 and 3.3 percentage points, respectively. The gain on Ans I is clearly larger than that on Ans. Adding the reliability prior further improves the four metrics by 1.1, 3.1, 1.2, and 1.7 percentage points. This shows that a historical reference beyond the current process evidence is helpful. When a tool returns normally but its evidence is questionable, the prior shows how the configuration has performed on related tasks and helps the verifier decide whether more evidence is needed. The prior also improves Ans I more than Ans. Both stages bring positive gains on all three benchmarks. Process evidence describes the current call, while the reliability prior provides a task-related historical reference. The two carry different information, and combining them outperforms verification without the prior. 

D. Analysis of Verification Strategies 

We compare the task performance and inference cost of different tool verification strategies. CRITIC [49] checks and revises an initial answer with tool feedback. Tools Fail [68] judges whether a tool output is reliable based on the task context. RSure-Agent verifies each tool observation before it enters the reasoning history. The verification uses process evidence and the task–tool reliability prior. The system accepts the observation, requests additional evidence, or rejects it. CRITIC and Tools Fail were not originally evaluated on remote sensing tasks. We adapt both strategies to RSure-Base. For CRITIC, the base agent first generates an initial answer. The model then calls remote sensing tools to check it and revises the answer based on the feedback. For Tools Fail, we use the checklist setting. The model judges tool outputs with the image, the task context, and the checklist. Accepted obser-vations enter the reasoning history, and rejection feedback is returned to the planner. The planner then adjusts later tool calls based on the feedback. Neither adaptation uses our reliability prior. All configurations use the same backbone, tool set, and test samples. The total tool-call budget is Hmax = 10 for all configurations. Calls made for the initial solution, evidence requests, and corrections all count toward this budget. E. Analysis of Observation Error Propagation 

Verification and evidence requests. We track what happens after an observation fails verification. Table VIII reports the results. Based on the current evidence, the verifier requests more information or rejects the observation. The backbone model then adjusts the tool arguments or switches to alterna-tive tools according to the feedback. Of the 1,229 tasks, 569 (46.3%) contain at least one observation that fails verification. Of these, 545 tasks request additional evidence, and 520 of them obtain at least one ac-cepted observation after the request. On all three benchmarks, more than 90% of tasks with failed observations request addi-tional evidence. For an observation that fails verification, the system usually seeks more evidence rather than rejecting the observation directly. On EarthBench, 72.2% of tasks contain at least one failed observation, higher than 42.4% on ThinkGeo and 37.6% on TerraLogic. This difference may come from how EarthBench tasks are organized. A single task usually comes with many files, and the agent needs to inspect, select, and combine information from different files several times. The execution produces more tool observations related to data selection and intermediate computation, and these observations more often need further verification. Of the 520 tasks with an accepted observation after the request, 246 (47.3%) are answered correctly. This ratio varies across benchmarks: 59.4% on EarthBench, 50.0% on ThinkGeo, and 34.0% on TerraLogic. The other 274 tasks still fail after obtaining accepted observations. Passing verification on a local observation does not mean that the whole task suc-ceeds. After a verified observation is obtained, later planning and multi-step reasoning still affect the final result. The system also rejects 52 observations. These rejected observations are not written to the verified history as accepted records. Sec-tions V-F and V-H further analyze the related failure modes. 

Propagation of wrong tool observations. Following the definition in Section III, we compare the error propagation rates of RSure-Base and RSure-Agent. Table IX reports the error propagation rates of RSure-Base and RSure-Agent. In RSure-Base, the error propagation rate exceeds 93% on all three benchmarks. In other words, in almost all tasks with wrong tool observations, at least one wrong observation is adopted by subsequent reasoning, and the wrong final answer is consistent with it. With the full RSure-Agent framework, the error propagation rate drops on all three benchmarks. It falls from 95.5% to 69.6% on EarthBench, a drop of 25.9 percentage points. It falls from 93.4% to 71.2% on ThinkGeo, a drop of 22.2 percentage points. It falls from 96.8% to 75.5% on TerraLogic, a drop of 21.3 percentage points. Because verification may trigger follow-up calls and change the later trajectory, the tasks with incorrect observations are not exactly the same for the two methods. Each rate is therefore computed over the tasks in which that method produces incorrect observations. These results show that the full framework substantially limits the effect of wrong tool observations on the final result.

We use the Efficiency metric of EarthBench to measure tool-call cost. For each task, the metric divides the actual number of calls by the number of calls in the expert reference, and then averages the ratio over tasks. Table X reports the tool-call efficiency on EarthBench. The overall tool-call ratio of RSure-Agent is 1.7891, lower than the 2.4146 of Earth-Agent with the same GPT-5 backbone, a relative reduction of 25.9%. All follow-up calls triggered by verification are included in the total count. Even with these calls, the overall ratio of RSure-Agent is still lower than that of Earth-Agent with GPT-5. The metric counts tool calls only and excludes the extra inference cost of the verifier. On every task subset, namely Spectrum, Products, and RGB, RSure-Agent has a lower tool-call ratio than Earth-Agent with GPT-5. The ratio drops from 3.5510 to 2.2697 on Spectrum, a relative reduction of 36.1%. It drops from 1.7154 to 1.6103 on Products, a relative reduction of 6.1%, and from 1.5312 to 1.2502 on RGB, a relative reduction of 18.4%. Together with Table IV, these results show that RSure-Agent improves task accuracy and reduces the tool-call ratio relative to Earth-Agent with GPT-5. The Overall ratios of all configurations are still above 1, so there is room to further reduce tool calls relative to the expert reference. 13 

H. Limitations 

The effect of RSure-Agent depends on the available data and the capabilities of existing tools. When the observations needed for a task are missing from the input data and no exist-ing tool can obtain them, further verification cannot produce new valid observations. For example, the period-mean case in Section V-F lacks September observations, which no tool can fill. Additionally, the verifiable observation protocol depends on tools that provide process evidence for their observations. The perception, measurement, and execution tools in this work return source evidence, intermediate results, and validity evi-dence, allowing the verifier to check whether observations are supported. For tools that return only final results without full process evidence, less information is available for verification. Finally, the reliability of tool observations is not the only factor that determines the task outcome. In Table VIII, some tasks still fail after obtaining accepted observations, and in Table IX, the error propagation rate of RSure-Agent is still 69.6% to 75.5%. These results show that more reliable tool observations reduce the effect of incorrect observations on subsequent reasoning, but the final task performance depends on both the quality of tool observations and the subsequent reasoning process. VI. C ONCLUSION 

In this paper, we present RSure-Agent, a framework for limiting the effect of incorrect tool observations on subsequent reasoning in remote sensing agents. Motivated by our analy-sis of 1,229 execution trajectories, the framework combines process evidence from a verifiable observation protocol with a task–tool reliability prior. The prior provides historical information about tool reliability across task types to support verification. Together, these sources guide decisions to accept observations, request additional evidence, or reject observa-tions. A. Top-Level Tool Descriptions 

perceive tool description 

Unified visual evidence for remote sensing. Use mode=evidence for image/figure VQA facts, document only for literal transcription of text/axes/legends, and scene for taxonomy-constrained classification. Use objects for instance boxes, regions for semantic masks, change for ordered before/after images, or measurement for two landmarks and a visible scale bar. For scene, put semantic land-use labels in label space and expect one exact label per source image. Never use the final answer letters as scene classes. Use objects or regions when later geometry must be computed; evidence does not choose the final answer. One scene backend is selected per image set and reused. Numerical measurements and coordinate-based spatial relations must be computed deterministically. Qualitative heading judgments may use visible front and rear features. 

measure tool description 

Produce one numerical spatial observation from explicitly declared image sources and a typed geometry specification. Each source states whether it needs instances, semantic regions, an ordered T1/T2 transition, or a caller-declared rectangular coordinate extent. The spec states the metric, labels, relation, distance, denominator, unit, and GSD. Sources must name raw visual evidence only. Use objects for discrete instances, regions for continuous or linear surfaces, change for a T1/T2 transition, and extent only for explicit frame coordinates. Put buffers, overlap, ratios, and zones in spec. The tool does not infer these from wording, read candidate answers, or use benchmark metadata. Prefer it to a hand-written spatial DAG when the required result is a count, area, fraction, percentage, distance, overlap, or boolean relation over visible imagery. 

execute tool description 

Compile and execute a deterministic DAG for raster for-mulas, statistics, time series, arithmetic, and spatial rela-tions over SpatialLayer artifacts. Connect ordinary stages with inputs.data=@node. Prefer this tool whenever the requested answer is a number, area, distance, percentage, trend, threshold result, or spatial count. Return the mea-sured value and compare it directly with answer choices when provided. Unknown operators and invalid units fail closed. 

retrieve tool description 

Retrieve a small set of trusted remote-sensing capabil-ity, algorithm-recipe, or domain-knowledge cards. Use it for formulas, sensor/physics concepts, or to identify the abstract workflow. Retrieval provides context, not a final numeric answer; execute calculations with rs execute.
