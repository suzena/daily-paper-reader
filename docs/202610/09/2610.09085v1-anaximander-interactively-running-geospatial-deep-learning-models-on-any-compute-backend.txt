Abstract 

Applying deep learning models to satellite imagery from within geographic information systems (GIS) remains high-friction for remote sensing practitioners. Models arrive in incompatible formats and target different compute environments, from local workstations to serverless cloud services. As a result, every evaluation demands custom deployment, tiling, and georeferencing code before a single prediction reaches the analyst’s map. This friction discourages systematic comparison in a domain where model choice directly affects operational outcomes such as field delineation, crop monitoring, and disaster response. We present Anaximander, an open-source system that unifies model source and compute location choice behind one interactive interface. The system’s backend is an inference server that loads models from multiple commonly used sources and serves them on any accessible compute backend. The server provides session management and model caching, and streams results back per tile. The backend is paired with a QGIS plugin that drives tiling, result reassembly, georeferencing, and real-time per-tile status visualization. An additional user-interface path injects layer legends as prompts into vision-language models. We demonstrate the system in a code-free side-by-side comparison of three heterogeneous models on an agricultural field delineation task: gpt-image-1 via a cloud API, Segment Anything Model 3 (SAM 3) on a remote GPU, and DelineateAnything on a local CPU. The inference backend and protocol are open-source and available at https://github.com/microsoft/nxmndr. 

Keywords: QGIS, Remote Sensing, Deep Learning, Computer Vision 

1. Introduction 

Applying deep learning models to satellite imagery is central to operational workflows across a diverse set of domains, such as agriculture (Robinson et al. 2026), disaster response (Krejcar and Namazi 2026; Akhyar et al. 2024), and environmental monitoring (Tadesse et al. 2024; Sartor et al. 2025). However, successful application of these models involves managing model loading, imagery alignment, and result reassembly, leading to practitioners spending more time writing integration code than running inference. The models that practitioners want to use arrive in heterogeneous formats and target distinct compute environments. Running a single candidate model on a raster covering an area-of-interest requires format-specific deployment code, tile-aligned inference, coordinate transformations, result assembly, and layer registration within geographic information system (GIS) software such as the popular open-source platform QGIS (QGIS Development Team 2026). Multiplied across the number of models a practitioner might evaluate, this integration work, rather than the inference itself, is the dominant bottleneck. arXiv:2610.09085v1 [cs.CV] 6 Oct 2026 2 Satej S. Soman et al. 

To address this gap, we propose Anaximander, a client-server system (Figure 1) that simplifies model source management and inference execution behind one interactive interface. One protocol separates where a model comes from (PyTorch, ONNX, HuggingFace, cloud API) from where it runs 

(local CPU, local GPU, remote GPU, hosted API), so both become a per-run dropdown inside a graphical user interface (GUI) rather than an integration project. The nxmndr backend exposes a remote procedure call (RPC) protocol to load models from PyTorch, ONNX, or HuggingFace sources and run them on a local CPU, local GPU, or remote GPU, plus an HTTP path to cloud application programming interface (API) models. The nxmndr-qgis plugin communicates with this backend from inside QGIS, handling tiling, georeferencing, result reassembly, and a live per-tile status overlay, plus a “Quick Labels” path that turns an existing QGIS layer legend into a structured prompt for a vision-language model. Spatial navigation inside QGIS becomes the evaluation interface: a practitioner pans or zooms to a region, loads the imagery on which a model should be run, and runs any registered model on the visible extent, observing predictions tile-by-tile as they arrive. The design is extensible: users can register their own model sources and compute backends. We release the system as open source to make model evaluations reproducible, to let the community extend the registry of model sources and compute backends, and to lower the barrier for GIS practitioners without machine learning tooling to adopt modern models in their existing workflows.

2. Related Work 

Several QGIS-integrated tools partially address the issues we have identified. Geo-SAM (Zhao, Fan, and Liu 2023) delivers interactive segmentation using features derived from the Segment Anything Model (SAM) (Kirillov et al. 2023) at millisecond latency on a local central processing unit (CPU), but only for the SAM model family. SamGeo (Wu and Osco 2023) wraps SAM variants (Carion et al. 2026) for geospatial use, runs on either CPU or GPU, and ships a FastAPI server that exposes segmentation over HTTP, so inference need not be colocated with the client. That server is likewise confined to the SAM family and is stateless per request: it accepts one image per call, leaving a client that tiles a raster to issue an independent request per tile. GeoAI (Wu 2026) is a multi-task, multi-family plugin spanning object detection, semantic and instance segmentation, and vision-language models, loading from PyTorch, ONNX, and HuggingFace sources and running on local CPU, CUDA, or Apple MPS. It also reaches a remotely served model, but only along one path: its vision-language features can target a vLLM endpoint, while its PyTorch, ONNX, and timm 

models execute in-process. Remote execution is therefore available for one model family rather than across the sources it supports. Deepness (Aszkowski et al. 2023; Febrita 2025) supports Open Neural Network Exchange (ONNX) detection, segmentation, and regression with a curated model zoo but is tied to a single model format. IAMAP (Tresson et al. 2026) extracts features from a range of foundation models on CPU-class hardware, but is scoped to feature extraction and likewise runs only locally. Each of these tools is constrained on at least one of: the supported model sources, the inference task, or where inference executes. Where remote execution is offered, it is bound to a single model family, and it is exposed as isolated per-request calls rather than as a protocol for streaming a tiled raster. In none of the existing solutions we surveyed is a practitioner able to direct the same inputs to multiple models and choose whether inference occurs, because the inference location is fixed by how the tool was installed and where its server, if any, was started. Additionally, no existing project couples source-agnostic remote delegation to a tile-streaming protocol with server-side session state, which is the combination Anaximander provides. That each of these solutions has independently re-implemented a serving pathway indicates that a thin GIS integration wrapper over a generic inference server such as Triton (NVIDIA 2026), TorchServe (The PyTorch Serve Contributors 2026), or Ray Serve (The Ray Contributors 2026) is insufficient for the specific demands of geospatial ML: model inference is closely tied to session and tile semantics, requires maintaining geographic metadata (coordinate reference system, geotransform, chip grid position), and incurs additional overhead to unify inputs from different imagery sources. Several packages, such as TorchGeo (Stewart et al. 2022), handle exactly those operations, but we choose to implement them on top of the GDAL library that ships with QGIS for deployment convenience, so the plugin adds no geospatial dependency to the user’s QGIS installation. TorchGeo also bundles a number of model implementations and weights, but is agnostic to where those models are deployed.

3.1 Inference Backend ( nxmndr )

Clients speak to nxmndr through a single service (Figure 2) that supports model loading, session management, single-shot prediction, and streaming tiled inference. The core of the service is a bidirectional-streaming channel, in which the client opens one server connection, streams tile chunks, and receives one response per completed tile tagged with the session and tile identifiers, per-tile timing, and the device that served it. This framing collapses thousands of tile submissions into a single long-lived stream, avoiding the connection setup cost that a unary-call-per-tile design would incur. The models running behind this protocol come from a variety of sources: local PyTorch weights, ONNX graphs, and HuggingFace repositories, and the server unifies them under a shared interface so the rest of the system can treat them identically. The server places every loaded model in a thread-safe LRU cache (default capacity 10) keyed by its specification. For PyTorch and HuggingFace models, the server moves the weights to the chosen device at load time. For ONNX graphs, it creates the ONNX Runtime session with that device’s execution provider, so the device is fixed when the session is created rather than chosen per call. A device dispatcher decides where the request actually runs. At startup the server enumerates the available GPUs (or CPU cores) into a device plan, and a round-robin cursor spreads requests across them. The dispatcher itself is backend-agnostic, and can delegate to specific computation environments. Alongside the gRPC service, the server can run an HTTP proxy to OpenAI or Azure OpenAI that discovers deployments from environment variables; the plugin’s Quick Labels path can send its requests through it. Adding a new backend means writing a new provider class, but the remote procedure call surface, session layer, and model registry are unchanged. Whichever backend runs the inference, a session layer tracks the state that outlives any single RPC call. Each session records the transport capabilities negotiated with the client (chunk size, in-flight tiles, and maximum tile size), the model it serves, per-tile counters for completed and failed tiles, and a creation timestamp. The server answers each tile individually, streaming back one response per tile, and concurrent sessions stay isolated from one another. 

3.2 Model Specification 

Registering new model types with nxmndr is done declaratively: the core library defines a ModelSpec 

that names the model’s format (PyTorch, ONNX, HuggingFace) and its source . Model weight loading and configuration are handled entirely through this interface, so the LRU cache, the session layer, and the device dispatcher are agnostic to the chosen model family, and a new family is added by registering a new spec type. Each tile response is decoded by result family. A dense output becomes a single-band label map: leading singleton axes are squeezed, a logit tensor is arg-maxed over its class axis, a two-dimensional integer map passes through (a floating-point one is kept as per-pixel values), and a bare class vector becomes a constant tile. Instance masks, which the model family’s adapter on the server resamples to the chip grid, become an instance map with identifiers unique within the run. The case study in Section 4 exercises the instance path with SAM 3 and DelineateAnything, while the rendered image from gpt-image-1 takes the Quick Labels path instead. 

3.3 QGIS Plugin ( nxmndr-qgis )

The plugin frontend (Figure 2, top) lets the user select input imagery using standard QGIS interface elements. Custom panels handle communication with cloud-based inference APIs, access to model hubs such as HuggingFace, and selection of local weight files; inference settings (tile size, device location) are specified after model selection. The plugin hooks into QGIS through its standard plugin-loading mechanism and adds a top-level “Models” menu to the QGIS menu bar with three actions: browse models, run Quick Labels, and 6 Satej S. Soman et al. 

open settings (Figure 4a). Two dock widgets appear on the right-hand side of the main window when the user invokes them (Figure 4b): a Model Browser for selecting and configuring models, and a Quick Labels dock for legend-driven prompt construction. The plugin attaches all panels, built with QGIS’s Qt bindings, through the QGIS plugin interface, so they inherit the host application’s raster layers, map extent, and project coordinate reference system without additional plumbing. To separate machine learning library dependencies from the versions pinned in QGIS’s included Python environment, local compute runs in a dedicated worker process with its own Python environment (NumPy 2, PyTorch, ONNX Runtime and the nxmndr package). The plugin starts it as a child process on the first local job or Quick Labels request, and it serves the same nxmndr 

gRPC service on a loopback port, so a local run uses the same tiled stream as a remote one. The plugin therefore installs no machine learning dependencies into the QGIS environment, and the same worker sends the Quick Labels cloud request. Once the user selects a model, the Inference Widget replaces the browser (Figure 6a). The user picks a task (segmentation, object detection, or embedding generation), maps raster bands to the model’s expected R/G/B inputs, sets a chip size and stride (default 512 pixels, with no overlap), and chooses a compute provider from the list configured in the settings dialog (Figure 5b). The tiling widget overlays a live chip grid on the QGIS canvas as rubber-band items and recomputes it whenever the canvas extent changes, so the preview follows the user’s pan and zoom. When the user clicks Run, the Inference Controller queues the run as a QGIS background task, which runs on a QGIS task thread and shows up in QGIS’s task manager. The task starts a server session, walks the chip grid and streams requests per tile to the nxmndr server through a client instantiated at the start of the run. As each tile’s status changes (pending, in-flight, OK, error, or cancelled) the task emits a signal back to the main thread, and the tile-status overlay recolors in real time (white, yellow, green, red, or dashed gray) as the task continues to dispatch. Because at most a server-negotiated number of tiles are in flight at once, resource use stays predictable; cancelling stops reading new tiles, ends the active stream, sends the server a session-cancel call, and marks every unfinished tile as cancelled. As tiles complete, the task writes each prediction into its window of a GeoTIFF on disk and flushes it, and the plugin adds that file to the active project as a raster layer as soon as the first tile is written, refreshing the layer as further tiles arrive (at most five times per second) and finalizing its styling when the job ends, so the user watches the result fill in while the server is still responding. The raster is georeferenced on the input layer’s own grid (its coordinate reference system and full geotransform) when GDAL can read the layer, or on the canvas coordinate reference system and the rendered extent’s grid for a layer it cannot, such as a web tile service, and the user can toggle, style, and overlay it like any other raster. A second, parallel workflow called “Quick Labels” (Figure 6b) bypasses the tiled gRPC pipeline: it extracts class names and RGB values from the renderer of a vector layer the user optionally picks in “Classes from” (or uses a default class list), injects them into a prompt template, and sends the prompt together with the current extent’s imagery to a cloud vision-language model such as gpt-image-1 , hosted on Azure AI Foundry or the OpenAI platform. The plugin georeferences the returned mask and adds it to the project as a raster layer, so the two workflows converge on the same kind of QGIS layer from the user’s perspective. We handle compositing and seams by allowing the model to see the full tile, but only a centered window of its output is composited into the mosaic. Where the stride, which sets the size of that window, is smaller than the chip, each tile is therefore predicted with context on all sides that is then discarded, which suppresses the edge artifacts that arise when a model is asked to label pixels at the limit of its receptive field. Partial tiles at the raster margin are padded to a full chip with the input’s nodata value (zero if it has none), marked invalid, and cropped back after inference, so the grid divides any extent without a separate boundary case. Written windows never overlap, because the stride equals the written window, so each output Microsoft 7pixel comes from exactly one tile and we perform no blending of class probabilities across tiles. Because compositing is per-pixel, an object crossing a tile boundary is labeled consistently but not 

identified as one object. For field delineation this means a parcel spanning two chips is delineated correctly as area while appearing as two instances, which matters for any downstream count or per-parcel statistic. In line with our philosophy that GIS analysts should be able to use the GUI’s capabilities to drive model evaluation and inference, we expect that a user would simply recenter the object split by a seam and run a smaller-scale inference call instead of relying on a general stitching procedure to handle all such tiling artifacts. In order to keep the client-side memory footprint of the system manageable, input rasters are never loaded entirely into memory. Each chip is a windowed read and each prediction is written to disk as it arrives, so client memory is bounded by chip size and the number of tiles in flight, which the server negotiates, rather than by the extent of the scene. A tile whose inference fails is masked as no data in the output raster, so it stays distinguishable from a background prediction, and it is also surfaced as an error in the live tile overlay at run time. 

4. Case Study: Agricultural Field Segmentation 

Anaximander’s core claim is that candidate-model comparison reduces to a sequence of menu selections rather than an integration project. We test this claim on an agricultural field boundary delineation task by running three architecturally different models on identical input imagery, with each model exercising a distinct combination of source family and compute backend: gpt-image-1 

(OpenAI), a cloud image-generation model driven by a segmentation text prompt, Segment Anything Model 3 (SAM 3) (Carion et al. 2026) downloaded from a gated HuggingFace repository onto a remote GPU, and a DelineateAnything (Lavreniuk et al. 2025) instance loaded from a local weights file on a CPU (Figure 3). The individual outputs illustrate a hypothetical investigation about which model fits this task best, but the primary point of the case study is to demonstrate the user’s ability to evaluate all three models without leaving the QGIS interface. 

4.1 Setup 

The input imagery is a 1,024 × 1,024 pixel crop (physical extent approximately 7.5 km × 7.5 km) of a Bing Maps satellite scene (© Microsoft) over a well-surveyed (Robinson et al. 2026) agricultural region in the Overberg District of Western Cape province in South Africa with visible field boundaries (Figure 3, top-left), loaded as a raster layer in QGIS. All three models receive exactly the same pixels. The plugin and server handle cutting the input into tiles and streaming pixels to, and results from, each model; we keep the plugin’s default 512-pixel chip size with no overlap, yielding four tiles per tiled run. The cloud path routes the imagery and a structured instruction prompt (full text in Appendix 2.1) to OpenAI’s gpt-image-1 image-editing endpoint and receives a single PNG mask in response. The remote-GPU path fetches SAM 3 weights from HuggingFace Hub, loads them on a GPU node, and ships the four tiles over gRPC. The local-CPU path loads a previously downloaded DelineateAnything weights file from disk into the nxmndr server that the plugin runs in a separate local worker process, and streams the tiles to it over gRPC to run on the host’s CPU. We intentionally hold tile size, band mapping (RGB), and input region constant so that any variation in output reflects model behavior rather than configuration. 

4.2 Cloud API: gpt-image-1 

The cloud path begins with gpt-image-1 (OpenAI), a multimodal image-generation model from OpenAI that accepts text and image inputs and returns image outputs. Because it is a generation model rather than a native segmentation model, we reach it through the plugin’s Quick Labels workflow (a single request to the cloud endpoint for the central 1,024 × 1,024 pixels of the map view) rather than through the tiled inference pipeline. We entered, in the panel’s custom-prompt field, a structured 8 Satej S. Soman et al. 

instruction prompt asking for a PNG instance-segmentation mask with a unique RGB color per field parcel (full text in Appendix 2.1). The plugin sends it with the imagery to OpenAI’s image-editing endpoint and georeferences the returned PNG into the active QGIS project. Deploying the model required selecting “Quick Labels” from the Models menu, choosing the configured gpt-image-1 

deployment, pasting that prompt into the custom-prompt field, and clicking “Generate Quick Labels”. The returned mask (Figure 3, top-right) captures the outline of some field parcels but shows substantial boundary inaccuracy, which is consistent with gpt-image-1 ’s role as a general-purpose image-generation model that treats segmentation as an image-to-image task rather than as dense per-pixel prediction, in line with reported limitations of general-purpose multimodal models on Earth-observation tasks (Zhang and Wang 2024). 

4.3 Remote GPU: Segment Anything Model 3 

The remote-GPU path exercises SAM 3, a promptable foundation segmentation model. We fetched its weights through the plugin’s ability to search HuggingFace, deployed them to a remote GPU node, and ran the standard tiled inference pipeline. We ran SAM 3 without geometric or text prompts to keep the comparison between deployment paths fair. Without a concept to score against, SAM 3’s per-query confidence is uninformative and standard score thresholding keeps no masks, so we started the server with score thresholding disabled, under which it selects instance masks geometrically instead. Unprompted, SAM 3 produced fragmented masks over roughly a third of the scene, many covering partial parcels rather than whole fields (Figure 3, bottom-left), which is an expected outcome for zero-shot promptable segmentation, not a fair evaluation of SAM 3 itself. The point of this run is that pulling a multi-gigabyte foundation model from a gated HuggingFace repository (requiring authorization handled by plugin configuration), deploying it to a remote GPU, and streaming tiles against it took a similar sequence of clicks as the cloud path. 

4.4 Local CPU: DelineateAnything 

The local-CPU path exercises DelineateAnything (Lavreniuk et al. 2025), a variant of the You Only Look Once (YOLO) detection architecture (Redmon et al. 2016) trained on 22 million field-boundary masks and purpose-built for agricultural field segmentation. We downloaded the weights from the project’s GitHub repository 1, uploaded them through the plugin’s local-file picker, selected the local CPU provider from the inference settings, and ran the tiled pipeline with a detection confidence threshold of 0.1. The output (Figure 3, bottom-right) captures most visible field parcels with tight boundaries that closely follow the underlying geometry, with visible artifacts where parcels cross tile edges, which is the expected result for a purpose-built model on in-distribution data run with non-overlapping tiles. This run’s purpose is to confirm that the local-CPU path, which shares the tiled streaming protocol with the remote-GPU path, assembles and georeferences CPU-served output correctly, and to provide the qualitative baseline against which the two foundation-model runs are compared.

4.5 Observations 

This case study is a qualitative demonstration, not a benchmark, and as such, we make no timing, accuracy, or statistical claims. What it does show is the core claim of the paper: the same plugin UI, driven by the same user, ran three models drawn from the source-and-compute matrix Anaximander claims to unify. These models were run on identical imagery, with identical georeferenced raster outputs landing in a single QGIS project. Switching among the three was a menu or dropdown choice, not an integration project: we wrote no Python code, converted no model format, implemented no tiling or georeferencing logic, and imported no per-backend client library. The individual outputs tell a less surprising story (that a purpose-built model fits a narrow task better than two zero-shot foundation models). 10 Satej S. Soman et al. 

5. Limitations 

In terms of scope, Anaximander’s protocol assumes that a model’s input is a single-resolution image tensor and that dividing a raster into square tiles covers the map extent. That assumption excludes important classes of geospatial models: those that require multi-scale image pyramids, auxiliary non-image inputs (digital elevation models, temporal stacks, text metadata), or non-image inputs entirely (point clouds, vector features). Supporting these would require extending the server’s streaming message schema and the plugin’s tile-generation logic. The current design accommodates the dominant pattern in remote-sensing computer vision but does not generalize to the full variety of inputs that recent geospatial foundation models are beginning to expect. Reassembly is similarly simple: each tile writes its own non-overlapping window, with no probability blending across seams, and instance identity is not reconciled across tile boundaries, so an object split by a tile edge appears as two instances (visible as seams in Figure 3, bottom-right). A related scoping choice is that Anaximander focuses exclusively on inference, so users must train or fine-tune models in an external pipeline and export weights in a supported format before deployment, unlike GeoAI or Deepness (Aszkowski et al. 2023), which bundle lightweight training paths alongside inference. Input preprocessing is future work: the server hands a torchvision or torchgeo model class the chip exactly as sent, unscaled and unnormalized, so pretrained weights from those catalogs need their training-time scaling and normalization exported into the model; a per-model preprocessing field, applied by the server and checked against the catalog’s published statistics, is the natural extension. 

6. Conclusion 

Geospatial practitioners have lacked a QGIS-integrated tool that is at once agnostic to where a model comes from and able to orchestrate tiled inference on either local or remote (served) compute through a single streaming protocol. Anaximander addresses this gap: it is an open-source system that unifies four model source families (PyTorch weights, ONNX graphs, HuggingFace repositories, and cloud APIs) and four compute backends (local CPU, local GPU, remote GPU, and cloud) behind a QGIS plugin, with one gRPC protocol for served models and an HTTP path for cloud APIs. Both the model zoos and the compute backend capabilities can be extended by users to fit their needs. Our case study exercises three of those combinations on a single agricultural scene (a cloud vision-language API, a remote GPU running a HuggingFace foundation model, and a local CPU running a YOLO variant) without writing integration code, with georeferenced outputs landing in the same QGIS project in each case. Several directions extend the system naturally. The most immediate are system benchmarks and a case study on non-RGB imagery. Supporting multi-scale image pyramids, auxiliary non-image inputs, and non-image geometries would broaden the class of models that fit the streaming protocol beyond its current single-resolution-image assumption. Integrating active-learning loops would turn the plugin’s tile-status overlay into a human-in-the-loop labeling surface, letting a user correct uncertain tiles without leaving the map. Exposing the server through managed-deployment templates (Kubernetes operators, serverless functions) would simplify large-area mapping for teams without dedicated GPU infrastructure. A less incremental direction is agentic use. The same gRPC surface that drives the QGIS plugin can drive an LLM-based planner that selects task-specific models dynamically: an autonomous GIS agent (Li and Ning 2023) can query the nxmndr model registry, pick the appropriate model for each subtask (e.g., building-footprint extraction, crop-type classification, change detection) and stream tiles through it, turning Anaximander into shared infrastructure for interactive and semi-autonomous Earth observation workflows alike. Appendix 1. User Interface Walkthrough 

This appendix gives a visual tour of the plugin’s main workflows. The interface is organized around four stages: locating the plugin inside QGIS, configuring credentials and server endpoints, browsing and selecting a model, and running inference on a raster. 

Appendix 1.1 Menu entry and panel location 

The plugin installs a top-level “Models” menu in the QGIS menu bar (Figure 4a). Selecting “Browse models” or “Quick Labels” from this menu activates a dock widget on the right-hand side of the QGIS main window (Figure 4b), where all subsequent configuration takes place; the settings action opens a separate dialog.

Appendix 1.2 Plugin settings 

The settings dialog groups four kinds of configuration into separate tabs (Figure 5): sign-ins for HuggingFace, OpenAI and Azure AI Foundry (Authentication), the addresses of deployed nxmndr 

server instances (Inference Providers), the OpenAI or Azure OpenAI endpoint that Quick Labels calls, directly or through the nxmndr proxy service (Quick Labels), and the environment of the plugin’s local worker process (Runtime). 

Appendix 1.3 Model browser 

Clicking “Browse models” surfaces a three-tab panel: Saved, a registry of previously-loaded models regardless of source, capped at twenty entries per inference provider to keep the list browsable; Hugging Face, a HuggingFace Hub search that reuses the user’s stored credentials when available; and Local, a local-file picker that accepts a path to weights (filtered to .onnx , .pt , and .pth files). Microsoft 13 Each tab emits the same selected-model payload, so the downstream inference configuration does not depend on where the model came from. A shared model key derived from the source descriptor (path, repository ID, or endpoint URL) lets the registry collapse duplicate entries for the same model, and the plugin checks at selection time that the server can serve the chosen combination (an ONNX graph, a HuggingFace repository, or a .pt /.pth checkpoint with a model class from the server’s list) and refuses any other with a reason; whether the weights load is left to the server, which rejects them when the session opens. 

Appendix 1.4 Inference configuration 

After a model is selected, the plugin offers two inference paths (Figure 6). The standard panel drives tiled inference through the nxmndr server: it accepts an input raster layer, a task (segmentation, object detection, or embedding generation), a band mapping, a chip size and stride, and a compute provider. The Quick Labels panel is an alternative path for cloud vision-language models that bypasses the tiled pipeline and calls the cloud endpoint from the plugin’s local worker process, directly or through the nxmndr proxy service: it takes an input layer, optional class definitions pulled from an existing layer’s legend (which are injected into the prompt), and a configured model endpoint.
